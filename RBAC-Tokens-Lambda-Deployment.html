Tokens, Lambda and Deployment

How an application proves who it is, where RBAC runs, and how code gets from GitHub to AWS without storing a password anywhere.

15 October 2026Written to be read start to finish

Part 1 · Start here

What a token actually is

A token is a temporary pass. Like a visitor badge at reception: you show your ID once, you get a badge, and the badge gets you through doors for a few hours. Nobody re-checks your ID at every door — they just look at the badge.

It expires

A stolen badge is useless tomorrow. That is the main reason tokens exist instead of passwords.

It is signed

It carries a mathematical seal. Anyone can check the seal is real; nobody can fake one.

It says who you are

Which application, which person, what it may do, and when it stops working.

The one sentence

The password is used once, to get a token. After that, only the token travels. If a token leaks, it dies on its own in twenty minutes. If a password leaks, it works until somebody notices.

Part 1 · The design

The two-endpoint pattern

One endpoint hands out a token. The other accepts it. This is the pattern you were asked to use, and it is the standard way almost every API on the internet works.

Part 1 · The detail

Why twenty minutes

Short expiry limits the damage window. If a token leaks, the attacker has twenty minutes, not a year. But too short and you spend all day fetching tokens.

ExpiryWhat it means
5 minutesVery safe, but 12 token calls an hour per application. Wasteful.
20 minutes chosen3 token calls an hour. A leaked token is dead before anyone could use it meaningfully.
1 hourWhat Microsoft Entra issues by default. Fine, but a longer damage window.
No expiryNot a token. That is a password with extra steps.
Refresh properly, not on a blind timer

Do not set a loop that fires every twenty minutes and hopes. Refresh at about 16 minutes — 80% of the life — or immediately when a call comes back 401. That way a clock drift, a restart or an early expiry never causes a failed request.

Part 1 · Important

Where the token is kept

This one matters

This token belongs to the application’s back end, not to a browser. It must be stored in the server’s own memory. If it is put in browser localStorage, any cross-site scripting bug on any page steals it, and whoever steals it can read every permission in that application until it expires.

PlaceSafe?Why
The back end’s memoryYesNever leaves the server. Dies on restart, which is fine — it just fetches another.
A server-side cache (Redis)YesNeeded only if many servers share one token. Still server-side.
Browser localStorageNoReadable by any script on the page. This is the classic token-theft route.
In the code, or in GitNoThat is the secret, not the token, and it belongs in a secret store.

The browser never needs this token. The person signs into your application in whatever way it already works; your back end then asks RBAC on their behalf.

Part 1 · The trade-off

What changes, and what it costs

Today Microsoft issues the token. In the new design RBAC issues it. That genuinely makes onboarding much easier — and it does have a price worth knowing before you present it.

Microsoft issues it (today)RBAC issues it (proposed)
Onboarding a new appSlow needs an Entra registration from ITMinutes an admin creates it in the console
Who stores app secretsNobody RBAC has no column for oneRBAC hashed, but it is now a target
Signing keyMicrosoft’s we only hold the public halfOurs a private key we must protect
If RBAC is breachedAttacker reads data, cannot forge tokensAttacker could forge tokens for any application
Revoking one appDisable it in EntraEasier delete the secret in RBAC
If Microsoft is downNo new tokens issuedUnaffected
One correction worth making out loud

Verifying a Microsoft token is not slow. It is a signature check against a key already held in memory — no call to Azure, no network hop, microseconds. Microsoft’s keys are fetched once and cached for 24 hours. So the reason to change is not speed. The real reason is onboarding friction: every new application currently needs its own Entra registration, and with many applications that is the slow part. That is a good reason on its own.

And one thing that cannot change

Microsoft stays regardless. Administrators still sign into the RBAC console with their Compass account, and the employee list still comes from the directory. Only the application-to-RBAC step moves. This is not a removal of Azure — it is a shortcut for one specific hop.

Part 2 · Hosting

What AWS Lambda is

Normally you rent a server: it runs all day, you pay all day, and you patch it. Lambda is the opposite. You hand AWS your code. It sits idle costing nothing. When a request arrives, AWS starts it, runs it, and stops it.

You pay per call

No request, no bill. Our free allowance is a million calls a month; we expect about 45,000.

Nothing to patch

No operating system of ours to update. AWS handles the machine entirely.

It scales itself

Ten calls or ten thousand, AWS runs as many copies as needed. No configuration.

The one quirk

If nothing has called it for a while, the first call waits a second or two while AWS starts it up. This is called a cold start. For RBAC it does not matter — the client library asks once per sign-in and then goes quiet.

Part 2 · The question asked

HTTP API or REST API?

These are the two kinds of front door AWS offers in front of a Lambda. The names are confusing — both speak ordinary HTTP and both are RESTful. The real difference is that HTTP API is the cheap, stripped-down one and REST API is the full-featured one.

FeatureREST APIHTTP API
Things we said we need
AWS WAF — the firewall that blocks attacksYesNo
Private endpoint — not reachable from the internet at allYesNo
Per-client rate limitingYesNo
Request validation — reject bad input before Lambda runsYesNo
Where HTTP API wins
Price per million calls (Mumbai)$3.50$1.05
Built-in JWT checkingNoYes
Slightly lower latency—Yes
Answer: REST API

The firewall and the private endpoint are both REST-only, and we want both. The usual argument for HTTP API is price — but at 45,000 calls a month that is $0.16 versus $0.05. We would be giving up our two most important network protections to save eleven paise a month.

A correction to the earlier document

An earlier note said “API Gateway HTTP API with a WAF”. That combination does not exist — AWS does not allow a WAF on an HTTP API. If REST API is chosen, the $0.10 difference should be corrected in the cost sheet; nothing else changes.

Part 3 · Deployment

Getting code from GitHub to AWS

When GitHub builds our code and deploys it, AWS has to be convinced GitHub is allowed to. There are two ways, and one of them is now considered the wrong way.

Part 3 · How

Setting up OIDC, in four steps

StepWhat you doWhere
1Add GitHub as a trusted identity provider — URL token.actions.githubusercontent.com, audience sts.amazonaws.comAWS, once per account
2Create a role that says what deployment is allowed to touch, with a trust rule naming our repository and branchAWS
3Give the workflow permission to ask for a proof, and tell it which role to useGitHub
4Delete the old access keys from GitHub secretsGitHub

The whole GitHub side is about six lines:

permissions:
  id-token: write          # lets the job ask GitHub for a signed proof
  contents: read

steps:
  - uses: aws-actions/configure-aws-credentials@v6
    with:
      role-to-assume: arn:aws:iam::<account>:role/rbac-deploy
      aws-region: ap-south-1

And the trust rule on the AWS side is what stops anybody else using it:

"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub":
        "repo:compass-group/rbac-portal:ref:refs/heads/main"
  }
}
Read that last line carefully

It says: only the main branch of that one repository may deploy. A fork cannot. A pull request from outside cannot. Another team’s repository cannot. Without that line the role would trust every repository on GitHub — which is the one mistake people make when setting this up.

Recent change — worth knowing

Repositories created after 15 July 2026 use a longer form that includes numeric organisation and repository IDs. If the trust rule uses the old short form, the deploy fails with “Not authorized to perform sts:AssumeRoleWithWebIdentity”. Check the exact value in the workflow log before locking it down.
